### Search ranking & database-side pagination (t7-search)

**Context**

- `GET /api/v1/recipes?search=…` calls `model.findAllForRanking` (`apps/api/src/modules/recipe/model.ts:410-432`). That function has **no `LIMIT`**. It loads every matching recipe plus **every version's** `productName` and `personalNotes` (≤10,000 chars, `packages/shared/src/schemas/recipe.ts:45`) into the API process. `rankRecipes` (`service.ts:444-465`) then lowercases and sorts the whole set, and `service.ts:595-596` slices one page. The browser receives one page, but each item still carries the undocumented `versions[]` array (`index.ts:236-245` serializes rows as-is; `FeedRecipeOutputSchema` has no `versions`).
- The non-search path (`findMany`, `model.ts:369-396`) is limited, but it also attaches every version's notes to each item (comment at `:388` says "for rankRecipes", which is stale).
- Predicates are leading-wildcard `ILIKE '%term%'` (`model.ts:128-150`). `schema.ts` has only B-tree indexes on `recipe` (`:160-205`) and `recipe_version` (`:252-276`), so every search seq-scans both tables. The parallel `COUNT(*)` holds a second pool connection (`Promise.all`, `:419-429`). The pool is `max: 10` with no `statement_timeout`/`connect_timeout`/`idle_timeout` (`packages/db/src/index.ts:7`). `search` has no length bound (`recipe.ts:163`).
- Validation outcome: the audit's server-memory, unbounded-load and seq-scan claims are **confirmed**. The reading "the browser paginates 1000 matches client-side" is **refuted**: the over-fetch is server-side. **Discovered in the same code path:** (1) `sortBy=rating` is accepted and offered in the UI, but `findMany`/`findAllForRanking`/`findStarred` order by `createdAt` (`model.ts:376,415,1212`). (2) No unique tie-break, so OFFSET pages over `likeCount` ties can repeat or skip rows. (3) JS `toLowerCase()` turns `İ` into `i̇` and disagrees with Postgres `ILIKE`, so some matched Turkish titles get score 0. (4) `\` is not neutralized in the ILIKE pattern. (5) `DrizzleQueryError.message` embeds bound params, so a failed search logs the raw term. (6) `errorHandler.ts:40` checks `err.name === 'PostgresError'`, but Drizzle ≥0.44 puts the driver error on `err.cause`.
- F11 (`openspec/changes/archive/2026-08-10-f11-advanced-search/design.md` D1) chose in-app ranking "for a recipe site with hundreds of recipes". It rejected SQL `CASE` ranking mainly because it would need a 3-field keyset cursor. This design keeps F11's offset fallback for search, so that objection no longer applies.

**Decisions**

- **D1: Score, order and paginate in SQL (one bounded page query + one COUNT).**
  - *Choice:* add `buildListPageQuery(opts)` and `findListPage(opts)` to `recipe/model.ts`. Build with the **core** select API: `db.select({ ...getTableColumns(recipes), author: { id: users.id, username: users.username, displayName: users.displayName } }).from(recipes).innerJoin(users, eq(users.id, recipes.authorId)).$dynamic()`. When search is active, left-join a grouped version-score subquery: `db.select({ recipeId: recipeVersions.recipeId, best: max(sql<number>\`(case when ${ilike(recipeVersions.productName, p)} then 2 else 0 end) + (case when ${ilike(recipeVersions.personalNotes, p)} then 1 else 0 end)\`).as('best') }).from(recipeVersions).where(or(ilike(pn, p), ilike(notes, p))).groupBy(recipeVersions.recipeId).as('version_scores')`. The score is `sql<number>\`(case when ${ilike(recipes.title, p)} then 3 else 0 end) + coalesce(${versionScores.best}, 0)\``. Then `ORDER BY score DESC, <sort key>, recipes.id`, `.limit(perPage).offset((page - 1) * perPage)`. `COUNT(*)` runs in parallel over the same `finalWhere` with no joins. `findMany` and `findStarred` delegate to it. `findAllForRanking` and `rankRecipes` are deleted. `getFeed`'s offset path keeps calling `findMany`.
  - *Alternatives:* Postgres FTS with `ts_rank` (changes matching semantics, see D3). Capped top-K candidate set plus JS ranking (still loads K × versions × notes, and drops relevant old recipes). Keep the relational `db.query.recipes.findMany` and add `extras`/correlated subqueries (hits the D03 alias bug where the relational API aliases `recipes`, so correlations break).
  - *Rationale:* exact parity with the F11 weights, best-version semantics and sort-key ties. API memory is O(perPage). One round trip per page plus the count. The core select API resolves correlations and joins correctly. Weights live in one SQL expression, and score and filter use the **same** `ilike` predicate, which fixes the `İ` mismatch by construction.
- **D2: Trigram GIN indexes (`pg_trgm`) for the three search columns, and a union-structured predicate.**
  - *Choice:* a `drizzle-kit generate --custom --name=enable_pg_trgm` migration containing only `CREATE EXTENSION IF NOT EXISTS pg_trgm;`. Then, in `schema.ts`, `index('recipe_title_trgm_idx').using('gin', table.title.op('gin_trgm_ops'))`, `index('recipe_version_product_name_trgm_idx').using('gin', table.productName.op('gin_trgm_ops'))` and `index('recipe_version_personal_notes_trgm_idx').using('gin', table.personalNotes.op('gin_trgm_ops'))`, with the migration generated by `make db-generate`. The search branch of `buildRecipeFilters` becomes `inArray(recipes.id, union(db.select({ id: recipes.id }).from(recipes).where(ilike(recipes.title, p)), db.select({ id: recipeVersions.recipeId }).from(recipeVersions).where(or(ilike(pn, p), ilike(notes, p)))))` (`union` from `drizzle-orm/pg-core`). This is semantically identical to today's `or(ilike(title), inArray(id, versions…))`, but it lets each branch bitmap-scan its own index. (`title ILIKE … OR id IN (hashed subplan)` cannot become a BitmapOr.)
  - *Alternatives:* no index (correct, but linear DB scans forever). Index only the version columns (cheaper, but the title branch stays a seq scan). FTS (D3).
  - *Rationale:* keeps exact substring semantics. The index is lossy and rechecked, so results are unchanged. pg_trgm is a **trusted** extension (installable by the DB owner without superuser) and ships with Postgres contrib. The indexes are schema-level features declared in `schema.ts`, matching the spirit of AGENTS.md. Implementation fallback if `inArray(…, union(…))` does not type-check in Drizzle 0.45: `sql\`${recipes.id} in (${titleIds} union ${versionIds})\`` with a D03 comment.
- **D3: Reject full-text search for now.**
  - *Choice:* stay with substring `ILIKE` semantics.
  - *Alternatives:* generated `tsvector` columns (`simple` or `turkish` config) + GIN + `ts_rank`/`websearch_to_tsquery`.
  - *Rationale:* FTS is lexeme-based (`yirga` ≠ `Yirgacheffe`; `websearch_to_tsquery` has no prefix `:*`), so it breaks existing spec scenarios. `ts_rank` is frequency-based, not the boolean 3/2/1 model. Generated columns cannot span `recipe` and `recipe_version`. The `turkish` stemmer mangles English (`kelime`→`kel`) while content is bilingual, and `simple` still does not give substring matching. It also needs `@@`/`ts_rank` operators in query code, a bigger rule change. It is a future option only if word-level relevance becomes a product goal.
- **D4: Version scope follows the filter; tie-breaks are deterministic; `sortBy=rating` is real.**
  - *Choice:* the score's version subquery uses the same version scope as the search predicate (any version today). Every offset ordering ends with `recipes.id` in the `sortOrder` direction. `rating` left-joins `db.select({ recipeId, avgRating: avg(userRecipeRatings.rating).as('avg_rating') }).from(userRecipeRatings).groupBy(recipeId).as('rating_agg')` and orders by `sql\`${ratingAgg.avgRating} desc nulls last\`` (or `asc nulls last`), with a D03 comment because Drizzle has no NULLS LAST helper in 0.45.
  - *Alternatives:* switch search to current-version-only now (owned by the data-layer version-semantics finding, and it changes results). Denormalize `avgRating` onto `recipe` (needs write-path maintenance and a backfill).
  - *Rationale:* fixes the "Top rated shows newest" bug and OFFSET duplicates without schema churn. The aggregate is computed in SQL per page query.
- **D5: Search input bounds and one normalization helper.**
  - *Choice:* `search: z.string().trim().max(200).optional()` in `RecipeFilterSchema`. An exported pure `normalizeSearchTerm(raw)` in `model.ts` strips `[%_\\]` and is used by `buildRecipeFilters`, the score builder, and `service.listRecipes` (`hasSearch`). No minimum length.
  - *Alternatives:* escape metacharacters instead of stripping (changes F11's "`%` alone is no search" semantics). Require ≥2–3 characters (rejecting 1-char searches with 400 breaks the per-keystroke UI until the t5 debounce lands, and is not needed once memory is bounded).
  - *Rationale:* closes the unbounded-input vector and the `\` escape bug while preserving F11 semantics. 1–2-char terms cannot use trigrams but are bounded by D6.
- **D6: Server-side statement timeout on the shared pool, and a 503 `QUERY_TIMEOUT`.**
  - *Choice:* in `packages/db/src/index.ts`, `postgres(url, { max: 10, connect_timeout: 10, idle_timeout: 20, connection: timeoutMs > 0 ? { statement_timeout: timeoutMs } : {} })`, where `timeoutMs` is parsed from `DB_STATEMENT_TIMEOUT_MS` (default 10000; invalid or negative falls back to the default). SQLSTATE `57014` (directly or on `err.cause` of a `DrizzleQueryError`) maps to 503 `{ code: 'QUERY_TIMEOUT' }` in `errorHandler.ts`, or in the `AppError` mapping if the error-contract track lands first. `listRecipes`/`listStarredRecipes` catch the timeout, log `warn` with `{ requestId, searchLength, pgCode }`, and rethrow a sanitized error with no `cause` message, so SQL and params never reach the logs.
  - *Alternatives:* a per-search `SET LOCAL statement_timeout` inside a transaction (raw SQL statement, and it costs an extra round trip). postgres.js client-side `query_timeout` (cancels client-side only, and its availability in 4.1.x is unverified).
  - *Rationale:* one global, server-enforced budget protects the 10-connection pool from any runaway query, not just search. Mapping to 503 gives clients a retryable signal instead of a hang or an opaque 500.
- **D7: List payloads drop `versions[]`.**
  - *Choice:* the core select projects only recipe columns and the author mini-projection.
  - *Alternatives:* keep the current-version fields for cards (not used by any list consumer: `RecipeCard` only renders an explicitly passed `version`).
  - *Rationale:* removes up to perPage × versions × 10 KB of unused text per list response and makes responses match the documented `RecipeListItemOutputSchema`.
- **D8: Record the decision and amend the rules.**
  - *Choice:* a new ADR in `docs/decisions.md` (next free number, ADR-015 at time of writing): "Database-side search ranking with pg_trgm (instead of in-app ranking or full-text search)". Amend the AGENTS.md "Database rules" first bullet and add a "Bounded reads" bullet (exact wording in `audit/t7-search.md` §4). Mirror both in `docs/architecture.md` "Portability Rules".
  - *Alternatives:* treat it as another silent D03 exception (that is how rule drift accumulated).
  - *Rationale:* `ilike` and `sql` fragments are already used everywhere, so writing the real rule down stops future plans (F13, F17) from being blocked by a rule the code doesn't follow.

**Risks / Trade-offs**

- [Risk] `pg_trgm` is unavailable in some image or managed DB (alpine contrib was not verified from a primary source). → Mitigation: a pre-flight task checks `pg_available_extensions` on `postgres:18-trixie` (compose) and `postgres:18-alpine` (CI). The fallback ships D1 without D2 (drop the custom migration and the index declarations). All memory and correctness requirements still hold.
- [Risk] `make db-reset` uses `drizzle-kit push`, which does not run custom migrations, so the index DDL fails with "operator class gin_trgm_ops does not exist". → Mitigation: add `psql -d brewform -c "CREATE EXTENSION IF NOT EXISTS pg_trgm;"` to `db-reset` before `$(MAKE) db-push`. A spec scenario covers it.
- [Risk] Migration-number interleaving with other wave-6 tracks' schema migrations breaks the extension-before-index order or the journal. → Mitigation: generate the custom extension migration first in the same PR as the index migration, rebase the journal, and re-run `make db-generate` (must print "No schema changes").
- [Risk] Creating GIN indexes (non-concurrently, inside drizzle-kit's migration transaction) briefly blocks writes on `recipe`/`recipe_version` during deploy. → Mitigation: the tables are small today (seconds). Note it in the PR and deployment docs, and run the migration in a low-traffic window if the catalogue has grown.
- [Risk] The `personal_notes` trigram index is large (on the order of the column size) and adds insert/update cost. → Mitigation: versions are insert-mostly. Measure `pg_relation_size` on seeded data in the verification task. If it becomes too large, a later change can drop that index, at the cost of the version branch seq-scanning `personal_notes`.
- [Risk] A 10 s global `statement_timeout` cancels legitimately long statements (seed, admin analytics, migrations run through the app pool). → Mitigation: drizzle-kit migrations use their own connection (`drizzle.config.ts`) and are unaffected. The seed's statements are short. `DB_STATEMENT_TIMEOUT_MS=0` or a larger value can be set per process. Document it in `.env.example` and `docs/deployment_coolify.md`.
- [Risk] The planner may still choose a seq scan on small tables, so index usage can't be asserted on seed data. → Mitigation: the EXPLAIN acceptance test sets `SET LOCAL enable_seqscan = off` to prove the indexes are *usable*, and asserts identical results with seqscan on and off.
- [Risk] Deep OFFSET pages still make Postgres score and sort all N matches. → Mitigation: the cost is DB-side, bounded by N and the statement timeout, with O(perPage) transfer. Search users rarely go past page 3 (F11 D1). Keyset-on-score remains a possible follow-up.
- [Risk] Case folding depends on the database ctype (`İ`→`i` under glibc/musl `en_US.utf8`, while `I`→`i`, not `ı`). → Mitigation: unchanged from today's filter behaviour. Score and filter now agree. A Turkish-specific collation or ICU is out of scope (noted as a follow-up).
- [Trade-off] Two `sql` fragments (`CASE` score, `NULLS LAST`) become D03 exceptions. → They interpolate Drizzle columns and bound params only, carry `// D03 raw-SQL exception:` comments, and are sanctioned by the new ADR.

**Migration / Rollout**

- DB migrations (in order): (1) the custom `enable_pg_trgm` migration (`CREATE EXTENSION IF NOT EXISTS pg_trgm;`). Snapshot untouched, since extensions are not tracked. (2) A generated migration creating the three GIN `gin_trgm_ops` indexes from `schema.ts`. No data backfill. `docker-entrypoint.sh` already runs `pnpm --filter @brewform/db run migrate` on boot, and CI (`pr.yml:122`, `ci.yml:106`) and `make test-db-provision` use `migrate`, so they pick both up. The role needs `CREATE` on the database (the DB owner in compose and Coolify).
- Env vars: new optional `DB_STATEMENT_TIMEOUT_MS` (default `10000`, `0` disables). Add it to `.env.example`, the `compose.yml`/`compose.production.yml` app environment (optional passthrough), and the env table in `docs/deployment_coolify.md`.
- API contract: list items lose the undocumented `versions[]`. `search` > 200 chars now returns 400. `sortBy=rating` now orders by rating. New 503 `QUERY_TIMEOUT`. Orderings gain an `id` tie-break. All are documented in OpenAPI and called out in the PR description.
- Rollback: revert the API code. The indexes and extension can stay (harmless). To remove them fully, delete the index declarations, run `make db-generate` (drop-index migration), then add a custom `DROP EXTENSION IF EXISTS pg_trgm;` migration. Setting `DB_STATEMENT_TIMEOUT_MS=0` disables the timeout without a deploy-time code change.
