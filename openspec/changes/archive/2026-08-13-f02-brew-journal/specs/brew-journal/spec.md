# Brew Journal

Owner-private brew event logging ("brew journal"): users record each time they brew a recipe with
actual measurements (yield, dose), free-text notes, and a 1–10 personal rating. Brew logs are
soft-deletable and visible only to their owner. Aggregate stats are computed per user (own,
authenticated) and per recipe (public). A "Brew Again" flow on the recipe detail page pre-fills
the log form from the recipe's current version.

## ADDED Requirements

### Requirement: Database table for brew logs

The system SHALL add a `brewLogs` table to `packages/db/src/schema.ts`:

```ts
export const brewLogs = pgTable(
  'brew_log',
  {
    id: varchar('id', { length: 36 }).primaryKey().$defaultFn(() => crypto.randomUUID()),
    userId: varchar('user_id', { length: 36 }).notNull().references(() => users.id),
    recipeId: varchar('recipe_id', { length: 36 }).notNull().references(() => recipes.id),
    recipeVersionId: varchar('recipe_version_id', { length: 36 }).references(
      () => recipeVersions.id,
    ),
    brewedAt: timestamp('brewed_at', { withTimezone: true }).notNull().defaultNow(),
    yieldActual: real('yield_actual'),
    doseActual: real('dose_actual'),
    notes: text('notes'),
    personalRating: integer('personal_rating'),
    createdAt: timestamp('created_at', { withTimezone: true }).notNull().defaultNow(),
    updatedAt: timestamp('updated_at', { withTimezone: true }).notNull().defaultNow(),
    deletedAt: timestamp('deleted_at', { withTimezone: true }),
  },
  (table) => [
    index('brew_log_user_brewed_idx').on(table.userId, table.brewedAt),
    index('brew_log_recipe_brewed_idx').on(table.recipeId, table.brewedAt),
    index('brew_log_deleted_at_idx').on(table.deletedAt),
    check('brew_log_personal_rating_check', sql`${table.personalRating} BETWEEN 1 AND 10`),
    check('brew_log_yield_actual_check', sql`${table.yieldActual} > 0`),
    check('brew_log_dose_actual_check', sql`${table.doseActual} > 0`),
  ],
);
```

`recipeVersionId` SHALL be nullable (a brew may predate version tracking or the version may be
unknown). No `onDelete` cascade SHALL be set on any FK — soft-deleted recipes/versions leave brew
logs in place and read paths filter them out. No index SHALL be added on `recipeVersionId` (no
query filters by it).

#### Scenario: Migration creates the table

- **WHEN** `make db-generate && make db-migrate` runs after the schema change
- **THEN** a new migration file `0014_<codename>.sql` is auto-generated by drizzle-kit
- **AND** it contains `CREATE TABLE "brew_log"` with all 12 columns, the 3 indexes, the 3 CHECK
  constraints, and the 3 foreign keys
- **AND** the migration applies without errors
- **AND** no generated SQL file is hand-edited

#### Scenario: Schema assertions pass

- **WHEN** `make test-specific filter=schema-indexes.test.ts`,
  `filter=schema-columns.test.ts`, and `filter=schema-constraints.test.ts` run
- **THEN** assertions for `brew_log_user_brewed_idx` (columns `['user_id','brewed_at']`),
  `brew_log_recipe_brewed_idx` (columns `['recipe_id','brewed_at']`), and
  `brew_log_deleted_at_idx` pass
- **AND** `brewLogs.createdAt`/`updatedAt` are asserted defined, `notNull`, with default
  expressions, and `deletedAt` nullable
- **AND** the three CHECK constraints are asserted

### Requirement: Shared input schemas for brew logs

The system SHALL add `packages/shared/src/schemas/brew-log.ts` exporting:

```ts
export const BrewLogCreateSchema = z.object({
  recipeId: z.uuid(),
  recipeVersionId: z.uuid().optional(),
  brewedAt: z.string().datetime().optional(),
  yieldActual: z.number().positive().optional(),
  doseActual: z.number().positive().optional(),
  notes: z.string().max(5000).optional(),
  personalRating: z.number().int().min(1).max(10).optional(),
});

export const BrewLogUpdateSchema = z.object({
  brewedAt: z.string().datetime().optional(),
  yieldActual: z.number().positive().nullable().optional(),
  doseActual: z.number().positive().nullable().optional(),
  notes: z.string().max(5000).nullable().optional(),
  personalRating: z.number().int().min(1).max(10).nullable().optional(),
}).refine(/* at least one field present */);
```

Both schemas plus inferred types SHALL be re-exported from `packages/shared/src/schemas/index.ts`.
`BrewLogUpdateSchema` SHALL allow `null` on every mutable field (to clear values) and SHALL reject
empty objects via a refine, matching the `CollectionUpdateSchema` pattern.

#### Scenario: Create schema validates input

- **WHEN** `BrewLogCreateSchema.safeParse` receives `{ recipeId: <uuid>, personalRating: 11 }`
- **THEN** parsing fails
- **AND** `{ recipeId: <uuid>, yieldActual: 36.5, doseActual: 15, notes: 'ok', personalRating: 8 }`
  parses successfully
- **AND** `{}` fails (`recipeId` required)

#### Scenario: Update schema requires at least one field and allows clearing

- **WHEN** `BrewLogUpdateSchema.safeParse` receives `{}`
- **THEN** parsing fails
- **AND** `{ notes: null, personalRating: null }` parses successfully

### Requirement: Response output schemas for brew logs

The system SHALL add `packages/shared/src/schemas/responses/brew-log.ts` exporting, each paired
with an inferred type export:

- `BrewLogOutputSchema` — `id`, `userId`, `recipeId`, `recipeVersionId` (nullable), `brewedAt`,
  `yieldActual` (nullable), `doseActual` (nullable), `notes` (nullable), `personalRating`
  (nullable), `createdAt`, `updatedAt` (ISO strings).
- `BrewLogListItemOutputSchema` — extends `BrewLogOutputSchema` with `recipeTitle` and
  `recipeSlug` from the joined recipe.
- `UserBrewStatsOutputSchema` — `totalBrews` (integer), `last30Days` (integer),
  `distinctRecipeCount` (integer), `firstBrewedAt` (ISO string, nullable), `lastBrewedAt`
  (ISO string, nullable).
- `RecipeBrewStatsOutputSchema` — `recipeId`, `brewCount` (integer), `avgBrewRating`
  (number, nullable — null when no brew has a personal rating).

The field names `brewCount`/`avgBrewRating` SHALL be used (NOT `avgRating`, which is the community
rating metric on `RecipeDetailOutputSchema` derived from `user_recipe_rating`). All schemas SHALL
be re-exported from `packages/shared/src/schemas/responses/index.ts` and the schemas barrel.

#### Scenario: Output schemas match service shapes

- **WHEN** the output of `service.listUserBrewLogs` items, `service.getRecipeBrewStats`, and
  `service.getUserBrewStats` is parsed by the corresponding schema
- **THEN** parsing succeeds for real service results (verified by the responses unit test with
  representative fixtures)

### Requirement: Brew log model layer

The system SHALL add `apps/api/src/modules/brew-log/model.ts` containing pure Drizzle data-access
functions (no business logic). All read queries SHALL filter `isNull(brewLogs.deletedAt)`.
Functions: `findById(id)`, `findByUserId(userId, page, perPage)` returning
`{ brewLogs, total }` ordered `brewedAt DESC` with joined recipe title/slug,
`findByRecipeIdAndUser(recipeId, userId, page, perPage)` with the same shape,
`create(data: typeof brewLogs.$inferInsert)`, `update(id, data)` (which SHALL set
`updatedAt: new Date()`), `softDelete(id)` (sets `deletedAt`), `getRecipeBrewStats(recipeId)`
(count + average of non-null `personalRating`), and `getUserBrewStats(userId)` (total, last-30-days
count, distinct recipe count, first/last `brewedAt`). List queries SHALL join `recipes` and filter
`isNull(recipes.deletedAt)`. Stats SHALL exclude brews of soft-deleted recipes.

#### Scenario: Soft-deleted logs are excluded from reads

- **WHEN** a brew log is soft-deleted via `softDelete(id)` and `findByUserId` runs for its owner
- **THEN** the deleted log is not returned and is not counted in `total`

#### Scenario: Logs of soft-deleted recipes are excluded

- **WHEN** the recipe of a brew log is soft-deleted and `findByUserId` or `getRecipeBrewStats` runs
- **THEN** that brew log is absent from the list and excluded from `brewCount`/`avgBrewRating`

### Requirement: Brew log service layer

The system SHALL add `apps/api/src/modules/brew-log/service.ts` with a module-scoped
`createLogger('brew-log-service')` logger and entry/exit debug logs plus error logs (with `err`)
on every public function. Functions:

- `createBrewLog(userId, data)` — SHALL throw `'RECIPE_NOT_FOUND'` if the recipe does not exist,
  is soft-deleted, or is neither public nor owned by the caller; SHALL throw
  `'RECIPE_VERSION_MISMATCH'` if `recipeVersionId` does not belong to that recipe.
- `updateBrewLog(userId, id, data)` and `deleteBrewLog(userId, id)` — SHALL throw
  `'BREW_LOG_NOT_FOUND'` when the log does not exist or belongs to another user (no ownership
  leakage), and `'FORBIDDEN'` is NOT required because non-ownership maps to not-found.
- `listUserBrewLogs(userId, page, perPage)`, `listRecipeBrewLogs(userId, recipeId, page, perPage)`
  (owner-scoped), `getRecipeBrewStats(recipeId)`, `getUserBrewStats(userId)`.

#### Scenario: Users cannot read or modify another user's brew log

- **WHEN** user B calls `updateBrewLog` or `deleteBrewLog` with user A's brew log id
- **THEN** the service throws `'BREW_LOG_NOT_FOUND'` and the log is unchanged

#### Scenario: Create validates recipe accessibility

- **WHEN** `createBrewLog` is called with a soft-deleted recipe id, or with another user's private
  recipe id
- **THEN** the service throws `'RECIPE_NOT_FOUND'` and no row is inserted

#### Scenario: Create validates version belongs to recipe

- **WHEN** `createBrewLog` is called with a `recipeVersionId` that belongs to a different recipe
- **THEN** the service throws `'RECIPE_VERSION_MISMATCH'`

### Requirement: Brew log CRUD routes

The system SHALL add `apps/api/src/modules/brew-log/index.ts` exposing a Hono router mounted at
`/api/v1/brew-logs` via `apps/api/src/routes/index.ts`, using the swappable `deps` middleware
proxy pattern, `zValidator(..., zodValidationHook)`, and the shared response helpers:

- `POST /brew-logs` (auth required) — validates `BrewLogCreateSchema`, returns the created log via
  `success(c, log, 201)`; maps `'RECIPE_NOT_FOUND'` → 404 and `'RECIPE_VERSION_MISMATCH'` → 400.
- `GET /brew-logs/:id` (auth required) — owner-scoped single get for the edit-form loader; maps
  `'BREW_LOG_NOT_FOUND'` → 404 (missing or foreign log).
- `PATCH /brew-logs/:id` (auth required) — validates `BrewLogUpdateSchema`, returns the updated
  log; maps `'BREW_LOG_NOT_FOUND'` → 404.
- `DELETE /brew-logs/:id` (auth required) — soft-deletes, returns `success`; maps
  `'BREW_LOG_NOT_FOUND'` → 404.

#### Scenario: Authenticated user creates a brew log

- **WHEN** an authenticated user POSTs `/api/v1/brew-logs` with a valid body referencing a public
  recipe
- **THEN** the response is 201 with the created brew log in the success envelope

#### Scenario: Unauthenticated create is rejected

- **WHEN** an unauthenticated request POSTs `/api/v1/brew-logs`
- **THEN** the response is 401 with an error envelope

#### Scenario: Owner updates and deletes their brew log

- **WHEN** the owner PATCHes `/api/v1/brew-logs/:id` with `{ "notes": "updated" }` and then
  DELETEs `/api/v1/brew-logs/:id`
- **THEN** the PATCH returns 200 with updated fields and the DELETE returns 200
- **AND** the log no longer appears in the owner's list

#### Scenario: Owner fetches a single brew log

- **WHEN** the owner GETs `/api/v1/brew-logs/:id`
- **THEN** the response is 200 with the brew log in the success envelope
- **AND** when another user GETs the same id, the response is 404

#### Scenario: Validation errors return 400

- **WHEN** an authenticated user POSTs `/api/v1/brew-logs` with `personalRating: 11`
- **THEN** the response is 400 with validation error details

### Requirement: Brew log list routes

The system SHALL expose owner-scoped paginated list routes:

- `GET /brew-logs` (auth required) — the caller's brew logs across all recipes, validated with
  `PaginationSchema`, newest `brewedAt` first, returned via `paginated(...)` with joined recipe
  title/slug per item.
- `GET /brew-logs/recipe/:recipeId` (auth required) — the caller's brew logs for one recipe, same
  pagination and ordering.

Both routes SHALL return only the caller's own logs; there is no public listing of individual
brew logs.

#### Scenario: User lists their own brew history

- **WHEN** an authenticated user with 3 brew logs across 2 recipes GETs
  `/api/v1/brew-logs?page=1&perPage=10`
- **THEN** the response is 200 with a paginated envelope containing 3 items ordered newest first,
  each including `recipeTitle` and `recipeSlug`

#### Scenario: Recipe-scoped list excludes other users' logs

- **WHEN** user A GETs `/api/v1/brew-logs/recipe/:recipeId` and user B also has logs for that
  recipe
- **THEN** only user A's logs are returned

#### Scenario: Unauthenticated list is rejected

- **WHEN** an unauthenticated request GETs `/api/v1/brew-logs` or
  `/api/v1/brew-logs/recipe/:recipeId`
- **THEN** the response is 401

### Requirement: Brew stats routes

The system SHALL expose aggregate stats routes:

- `GET /brew-logs/stats/user` (auth required) — returns `UserBrewStatsOutputSchema` for the caller.
- `GET /brew-logs/stats/recipe/:recipeId` (optional auth) — returns
  `RecipeBrewStatsOutputSchema` aggregating ALL users' non-deleted brew logs for the recipe;
  `avgBrewRating` SHALL be null when no brew has a personal rating.

#### Scenario: User retrieves their brew stats

- **WHEN** an authenticated user with 5 brew logs (2 in the last 30 days, across 3 recipes) GETs
  `/api/v1/brew-logs/stats/user`
- **THEN** the response is 200 with `totalBrews: 5`, `last30Days: 2`, `distinctRecipeCount: 3`,
  and non-null `firstBrewedAt`/`lastBrewedAt`

#### Scenario: Visitor retrieves public recipe brew stats

- **WHEN** an unauthenticated request GETs `/api/v1/brew-logs/stats/recipe/:recipeId` for a recipe
  with 4 brews of which 2 have personal ratings 8 and 10
- **THEN** the response is 200 with `brewCount: 4` and `avgBrewRating: 9`

#### Scenario: Recipe with no rated brews returns null average

- **WHEN** the recipe has brews but none with a personal rating
- **THEN** `avgBrewRating` is null and `brewCount` reflects the brew total

### Requirement: Brew log form page with create, edit, and prefill

The system SHALL add `BrewLogFormPage` serving both `/brew-logs/new` and `/brew-logs/:id/edit`
(both `RequireAuth`, both with loaders). The shared `BrewLogForm` component SHALL provide fields
for `brewedAt` (native date/datetime input), `yieldActual`, `doseActual`, `notes`, and
`personalRating` (1–10), with client-side constraints matching the shared schemas. On create, the
loader SHALL read `recipeId` (required) and `recipeVersionId` (optional) from the URL search
params, fetch the recipe, and pre-fill `doseActual`/`yieldActual` from the version's parameters as
starting points. On edit, the loader SHALL fetch the existing log and reject non-owners. Submit
SHALL POST/PATCH via `brewLogApi` and navigate back to the brew log list on success.

#### Scenario: Brew Again prefill

- **WHEN** an authenticated user opens `/brew-logs/new?recipeId=<id>&recipeVersionId=<vid>` from a
  recipe whose current version specifies 15g dose / 250g yield
- **THEN** the form shows that recipe with `doseActual` pre-filled to 15 and `yieldActual` to 250,
  both editable

#### Scenario: Edit round-trip

- **WHEN** the owner opens `/brew-logs/:id/edit`, changes the rating, and submits
- **THEN** a PATCH is sent with only the form values and the user lands on the updated list
