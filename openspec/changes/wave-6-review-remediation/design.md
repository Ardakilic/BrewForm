## Goals / Non-Goals

**Goals**
- Fix the four must-fix findings before any image is published: editable recipes with deleted links, a restore that never leaves a mixed database, bounded memory for `/uploads`, and a working admin user search.
- Close the access gaps and races: cross-recipe replies, double comment deletes, parallel wrong-password logins, the QR existence oracle, a version diff that bypasses the author-only rule.
- Make deploys safe for self-hosters: no demo accounts with a published password, a build context without local data, backups that survive a busy night, documented front-proxy and rollback contracts, and secrets off command lines.
- Remove the web data-loading regressions: stale URL writes, a rating that blanks the page, login redirects to element-less routes, private data left on screen after sign-out, wrong rollbacks, a stale collections card.
- Make the contrast rules hold for real backgrounds and the whole app, and make `niceTicks` terminate.
- Make the specs truthful again (the raw-SQL registry, the seed contract, the contradicted wave-6 requirements) and enforce the registry with a test.
- Delete the dead code the review found, and record only what stays deferred in the debt ledger.

**Non-Goals**
- No new features beyond the fixes. No ADR (ADR-022 stays the next free number).
- No `SEED_DEMO_DATA` override (`audit/decisions.md` §2).
- No change to the `TRUSTED_PROXIES` default (#13 is fixed in docs).
- No `COLLATE "C"` rebuild of the identifier indexes (#26 is fixed in the query).
- No advisory lock for concurrent migrators (multi-replica serve stays unsupported, D99.45).
- Items that stay deferred are listed under Open Questions → "Follow-ups recorded in the debt ledger".

### API: recipes, comments and search (r1)

1. **References are re-checked only when they are new (#1).**
   - Choice: `updateRecipe` passes `validateReferences` only the taste notes and equipment not on the current version, and `vendorId`, `coffeeVarietyId` and `beanId` only when they differ from the stored value (a private `isNewReference(value, stored)`, the rule `beanId` already followed). An unchanged `coffeeVarietyId` keeps the stored `coffeeVarietyName` without a lookup. `mergeRecipes` drops taste notes and equipment whose catalog row has `deletedAt`, using the relation rows already loaded, and logs the dropped counts.
   - Alternatives: look the variety up including deleted rows to refresh its name (a new model function for a cosmetic effect; renames never propagated to recipes anyway); a "skip validation" flag on `createRecipe` for merges (widens the create path for one caller).
   - Behaviour notes: a newly added deleted id is still rejected and the detail names only it; recipes keep links to deleted catalog rows, as forks and absent keys already did; the equipment compatibility check is unchanged (`getEquipmentByIds` does not filter `deletedAt`).
2. **Replies stay in their recipe's thread (#5, closes D99.42).**
   - Choice: `createComment` answers `COMMENT_NOT_FOUND` (404 "Parent comment not found") when the parent belongs to another recipe, on the same line as the missing-parent check, and again for the top-level comment that thread flattening resolves (a legacy cross-recipe chain passes the first check). `findByRecipe` loads replies with `eq(comments.recipeId, recipeId)`, so rows stored before the fix never show in another thread.
   - Alternatives: a typed 400 (D99.42 suggested "400/404"; 404 matches the missing-parent answer and reveals nothing); a data migration deleting existing cross-recipe rows (the read filter hides them, and they exist only through direct API use).
3. **A comment delete decrements only when it deleted (#14), on top of a test rework.**
   - Choice: `deleteComment` uses the result of `softDelete`; `null` means another request won, so it answers `COMMENT_NOT_FOUND` (404, the answer a sequential second delete already gets) and skips the decrement. E1 extends this (Extras E1).
   - Facts: under READ COMMITTED the second `UPDATE … WHERE deleted_at IS NULL` waits for the first and then re-evaluates its WHERE on the updated row, so it matches nothing (Context7 `/websites/postgresql`, 13.2.1 "Read Committed Isolation Level").
   - Alternatives: `GREATEST(comment_count - 1, 0)` (hides future bugs); a CHECK `comment_count >= 0` (turns a cosmetic drift into 500s); a transaction around soft delete and decrement (fixes a different crash window that create also has).
   - Prerequisite: `comment/service.test.ts` tested an inline copy of the service that still used the removed `getRecipeAuthorId` flow and had no visibility gate. R1.8 (task 8.1) runs the existing properties against the real functions through `deps` before any new assertion.
   - The other stored counters are correct: `likeCount` changes inside `toggleLike`'s transaction only when its `returning` produced a row, `forkCount` only inside the fork transaction; every other count is computed at read time.
4. **Recipe relation arrays are bounded (#15).**

### Deploy, operations and seed (r3)

1. **Restore into a scratch database and swap it in only on success (#2).**

  - Alternatives: comments only, leaving recipes and collections to D99.26 (the recipe and collection pages would keep showing the name the comment fix hides, against the privacy text); cascade soft-delete of the account's recipes and collections (D99.26's content decision, removes content other users collected or forked, needs a backfill, and through E1 would also delete the recipe author's replies); filtering deleted authors inside `listableRecipeCondition` (a join on every listing and a change to the central visibility rule); a `deleted: true` marker (a new field on eight schemas, where `null` already exists in the comment schema and the web).
  - Edge cases: cached collection responses can show the old identity until their TTL ends (at most 10 minutes; correctness never depends on the cache); `authorId` stays in payloads (an opaque id needed for own-comment checks); a banned, not deleted, user is unaffected; comment text that mentions an old `@username` is user content and is not rewritten.

## Risks / Trade-offs

**Cross-track**
- [Many groups edit the same files (see Cross-track integration item 3)] → Mitigation: work in `tasks.md` order on one branch; each later task names the earlier change it builds on; `AGENTS.md`, `docs/architecture.md` and the ledger get one pass each.
- [A spec header that differs from the main spec only in letter case passes `validate` but aborts `archive`] → Mitigation: the trial archive on a scratch copy in task 21.8, before the real archive.
- [PR #172 grows past 103 commits and a reviewer sees two changes] → Mitigation: one change folder per wave, pathspec commits per group, and the PR description gains a section for this change (task 22.3).

**Database and API**
- [Migration 0020 rewrites `recipe` and its indexes under an `ACCESS EXCLUSIVE` lock] → Mitigation: seconds at most for a self-hosted catalogue; compose applies it in the `migrate` one-shot before the api starts. Under Coolify's rolling update the old container's recipe queries wait on the lock and may hit `DB_STATEMENT_TIMEOUT_MS` (503 `QUERY_TIMEOUT`) for that moment; the upgrade notes mention the one-time rewrite.
- [Date filters reject timestamps (BREAKING)] → Mitigation: the web only ever sends `YYYY-MM-DD` and drops anything else from the URL; the PR and `docs/api.md` state the change; OpenAPI already declared `format: date`.
- [The QR route answers 404 instead of 403] → Mitigation: no client depends on 403 (the web treats every failure alike and hides the QR card for draft/private recipes).
- [Re-sending the current `coffeeVarietyId` no longer refreshes a renamed variety's name] → Mitigation: renames never propagated to recipes anyway; re-picking the variety refreshes it.
- [Consume-first counters can exceed `points` under a burst, and a reward after expiry grants one extra attempt] → Mitigation: fixed windows (no longer lockouts) and at most one extra attempt per success.
- [The store-recovery hook overrides a library internal (`_getRateLimiterRes`)] → Mitigation: `rate-limiter-flexible` is pinned to 11.5.0 and the test drives the real library path, so a rename on upgrade fails CI.
- [`lower(unknown)` resolution could be ambiguous on some server] → Mitigation: the DB-backed compile and EXPLAIN test; the `::text` cast fallback.
- [Uploads are cached by browsers for a year] → Mitigation: keys are server-generated and never rewritten. A soft-deleted photo's file stays fetchable and now cacheable (pre-existing; noted on D99.41).
- [Mail logs lose the SMTP reply text] → Mitigation: `code`, `command` and `responseCode` remain, which identify credentials, network and recipient failures.
- [Admin and catalog searches no longer treat `%`/`_` as wildcards, and a whitespace-only `search()` returns `[]`] → Mitigation: no UI documented the wildcards; the routes' validators never send an empty term.
- [Deleting your own top-level comment also removes the recipe author's replies to it] → Mitigation: the UI already hid them; the narrow race (a reply inserted during the cascade) is accepted and documented.
- [The first deploy changes visible comment counts (negative values, hidden replies of deleted comments and cross-recipe replies stop counting)] → Mitigation: only drifted rows change, each repaired id is logged with its old and new value, and cached recipe responses catch up within their TTL.
- [The recount runs on every migration run, so a large catalogue lengthens the deploy] → Mitigation: one indexed count per live recipe in batches of 500, each statement far below the 10 s statement timeout; seconds for a self-hosted catalogue.
- [A comment inserted before the recount read whose increment runs after the repair leaves that count one too high] → Mitigation: the next migration run repairs it; the compare-and-set never overwrites a concurrent increment or decrement.
- [A failed recount only warns, so drift can survive a deploy] → Mitigation: the warning and the error line are in the `migrate`/api logs; `make db-recount-comments` and the CI smoke test exit non-zero; the next start retries.
- [The database-error log scan covers a fixed list of files] → Mitigation: the AGENTS.md logging rule and review cover new files; adding a file to the list is one line with its reason.
- [Deleting mirror tests could drop an assertion] → Mitigation: each behaviour a mirror asserted gets a test of the real function before its copy is deleted (tasks 9.4, 9.5), and the API coverage floor is checked in task 9.6.
- [Recipe and collection author/owner fields can now be `null` (an API contract change for clients)] → Mitigation: comments already allowed it; the web ships in the same change; OpenAPI, `docs/api.md` and the PR description document it.
- [A cached collection response can show a deleted account's identity for up to 10 minutes] → Mitigation: the spec states it; correctness never depends on the cache.
- [The recipe list switches from `innerJoin` to `leftJoin` on `users`] → Mitigation: every recipe has a non-null `author_id`, so no row appears or disappears, and the EXPLAIN test re-runs (task 8.11).
- [Threads past 20 replies show only the first 20 plus a hint; the 21st reply is stored, counted and notified but not readable yet] → Mitigation: D99.64 records the "load more" endpoint and button.
- [The replies read becomes one lateral query instead of two plain ones] → Mitigation: served by `comment_parent_created_idx`; if a plan regresses, a per-parent query is a local change in the model.
- [Admins lose an undocumented way to diff private recipes] → Mitigation: there was no UI path; admin moderation uses `/api/v1/admin/*`.

**Deploy**
- [A restore temporarily needs room for a second copy of the database, and a crash between the drop and the rename leaves only `<db>_restore`] → Mitigation: the runbook says how to rename it or restore the safety dump; the window lasts milliseconds.
- [One-shot backups no longer prune, so disk grows by one pair per manual backup] → Mitigation: the scheduled run prunes at its next interval.
- [After upgrading, the backup service turns unhealthy if uploads archives were failing silently] → Mitigation: that is the intended signal; §16 points at `make prod-logs`.
- [Fresh production installs start without sample recipes, and existing installs keep their demo accounts] → Mitigation: README and both guides say so, with the cleanup step (Migration Plan step 4).
- [A future `.env.example` in another folder needs its own exact-path exception] → Mitigation: the `.dockerignore` comment says so, and the dockerignore test fails if a template disappears from the context.
- [Operators behind a plain nginx keep a spoofable client IP until they add the header] → Mitigation: the guide's snippets, the `.env.production.example` comment and the PR upgrade notes.

**Web**
- [The sitemap moves: an older web image in front of a new API does not proxy `/sitemap.xml`, and Search Console still holds the old URL] → Mitigation: deploy both images with the same tag (both guides do); the old URL answers 301; the upgrade notes ask operators to resubmit `/sitemap.xml`.
- [Follow treats 409/404 as success] → Mitigation: those statuses mean "already in the requested state"; every other failure still rolls back with a toast.
- [Visible token changes in every theme (lighter dark text, darker light tertiary and status colours, dark text on gold badges)] → Mitigation: the contrast matrix locks every allowed pair; manual check 20.4 adds a pass over cards, popups, compare and diff pages.
- [A background action with a dead session gives a toast instead of a redirect, and the navbar stays signed in until the next navigation] → Mitigation: the next guarded navigation redirects to login; E7 mirrors sign-out across tabs.
- [Signing out now always lands on `/`, even from a public page] → Mitigation: intended (user default).
- [A tab in the middle of a form loses its unsaved input when another tab signs out] → Mitigation: intended, the session is gone; tabs still running the previous bundle listen only after a reload.
- [E9's stronger literal guard flags strings added by other groups in this change] → Mitigation: intended; each gets a key, never an allowlist entry.
- [E2's module-level registry is shared by every router in one test file] → Mitigation: each test ends with its timers fired or the component unmounted (Testing Library's cleanup unmounts).

## Migration Plan

1. **Where it lands.** Every task commits to `wave-6-audit-remediation`; PR #172 gets the new commits and an extended description after the user approves the push (task 22.5). `publish` runs only on `main` after all jobs pass, so no image with the old defects is ever published.
2. **Database.** One generated migration, `0020_<generated name>.sql`: `recipe.created_at` becomes `timestamp(3) with time zone`. It rounds existing values to the millisecond (order kept, ties broken by `id`) and rewrites the table once under an exclusive lock. Compose applies it in the `migrate` one-shot before the api starts; Coolify's API entrypoint applies it on the first start of the new container. No data backfill. `make db-reset` (push) creates the column with precision 3 directly. A restored dump from before 0020 brings the old type back until `migrate` re-applies the migration, which happens on the `up -d` that ends `make prod-restore`.
3. **Deploy order.**
   - Compose: `git pull` first (the restore, backup and `.dockerignore` fixes live in the repository, not the image), then `make prod-pull` and `make prod-up`.
   - Coolify: redeploy the API and the web resources with the same tag.
   - The API and web images must move together, because the web edge now proxies `/sitemap.xml`.
4. **Demo accounts on existing installs.** The seed runs only on an empty database, so installs created before this release keep `alice`, `bob`, `charlie`, `diana` and `evan` with the published password. Both guides gain the cleanup step: sign in as the admin, Admin → Users, search `example.com`, delete the five accounts (a soft delete with an audit-log entry; deleted accounts cannot sign in), then review recipes and comments they posted after the install date (task 18.3). Fresh production installs create only the admin and the reference catalogues.
5. **Sitemap.** After the upgrade, `robots.txt` announces `<public origin>/sitemap.xml`; operators who submitted `/api/v1/sitemap.xml` in Search Console resubmit the new URL (the old one answers 301). Split-domain Coolify setups without `API_UPSTREAM` still serve the SPA at `/sitemap.xml` on the web origin (D99.58 stays open with the new path).
6. **Read-side changes without data changes.** E11 masks deleted accounts from the first request after the upgrade, including accounts deleted earlier (collection caches catch up within their TTL); E10's relation name is not in the snapshot; nothing to backfill (stored comment counts are repaired by the recount, step 11).
7. **Operator follow-ups.** Behind a plain nginx, add `proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;` and raise `client_max_body_size`. If `S3_PUBLIC_URL` ever had a trailing slash, repair the stored `//` photo URLs once with the documented `psql` statement.
8. **Rolling back this release.** An image tag from before this change but after wave 6 runs against the migrated database: it reads and writes `Date` values, which are already milliseconds, so no restore is needed. The repository's new compose file also runs those images (they support the `migrate` mode). Migrations are never rolled back automatically.
9. **The pre-wave-6 rollback floor.** This compose file runs only images with the `migrate` entrypoint mode (wave 6 and later); a pre-wave-6 image would start `migrate` as a server that never exits. To go back further: stop `api`, `web` and `backup`; restore the pre-upgrade dump (written as `db-<timestamp>.dump`) with this file's `restore` service directly (`docker compose … --profile restore run --rm -e RESTORE_DB_DUMP=<dump> restore`), not with `make prod-restore`, whose final `up -d` would migrate the dump forward again; then `git checkout <old tag> -- compose.production.yml`, set that release's `IMAGE_TAG` and follow its instructions (task 17.11). Coolify keeps its rollback note: change the tag and restore the backup taken before the upgrade.
10. **CI.** Every push to the PR runs the dockerignore test and the compose smoke test with the restore round-trip in the `images` job. After the merge, the post-merge checks of wave-6 29.14 (task 22.7) confirm the publish ordering and the GHCR tags.
11. **Comment counts.** Every migration run ends with the comment-count recount: the compose `migrate` one-shot (also after `make prod-restore`, whose final `up -d` re-runs it on the restored data), every Coolify API start with `RUN_MIGRATIONS` left on, and `make db-migrate` in development. The first run after this upgrade repairs the counts that drifted before (double deletes, hidden replies of deleted comments, cross-recipe replies) and logs each repaired recipe id with its old and new value; later runs normally print `repaired 0`. Nothing to do by hand; a failed recount prints a warning, the start continues and the next start retries. Rolling back to an older image needs nothing: older code keeps maintaining the counter the same way.
