## Why

Users currently have only two ways to organise recipes: **favourites** (a single flat boolean flag) and **setups** (equipment configurations, not recipe groupings). There is no way to curate a named, themed set of recipes — "My Morning V60s", "Espresso Dial-In Log", "Weekend Guests" — or to share that curation publicly. This limits both personal organisation (a power user may want dozens of groupings) and discovery (other users can't browse a curated playlist of recipes the way they can on music/film platforms).

Recipe collections ("playlists for recipes") fill both gaps: a first-class, reorderable, many-to-many grouping with public/private visibility, surfaced on user profiles and on recipe detail pages.

## What Changes

- **Two new Drizzle tables** in `packages/db/src/schema.ts`: `collection` (main entity, soft-deletable, owns `visibility`) and `collection_item` (join table with `sortOrder` + `createdAt` audit column, composite unique on `(collectionId, recipeId)`). Relations added to `usersRelations`, `recipesRelations`, and two new relations blocks. Migration auto-generated via `make db-generate`.
- **New shared Zod schemas** in `packages/shared/src/schemas/collection.ts`: `CollectionCreateSchema`, `CollectionUpdateSchema`, `CollectionAddRecipeSchema`, `CollectionReorderSchema`, `CollectionListFilterSchema`. Re-exported from the schemas barrel.
- **New response Output Schemas** in `packages/shared/src/schemas/responses/collection.ts`: `CollectionOutputSchema`, `CollectionListItemOutputSchema`, `CollectionDetailOutputSchema`, `CollectionItemOutputSchema` — derived from the actual `service.ts` return shapes (joined author, joined recipe items, computed `recipeCount`). Re-exported from both barrels.
- **New API module** `apps/api/src/modules/collection/` following the 3-layer pattern: `model.ts` (pure Drizzle data-access, `isNull(deletedAt)` everywhere) → `service.ts` (ownership + visibility permission checks, structured logging, string-error throws) → `index.ts` (8 Hono routes, each with `describeRoute()` OpenAPI metadata, `zValidator`, `zodValidationHook`).
- **Route registration** in `apps/api/src/routes/index.ts`: `routes.route('/api/v1/collections', collection)`.
- **New `Collections` OpenAPI tag** registered in `apps/api/src/routes/openapi.ts` `tags` array.
- **OpenAPI coverage test** updated: add `/api/v1/collections` to `IN_SCOPE_BASE_PATHS` in `openapi.coverage.test.ts`.
- **Frontend**: two new pages (`CollectionListPage`, `CollectionDetailPage`), four new components (`CollectionCard`, `AddToCollectionModal`, `CollectionRecipeList`, `AddToCollectionButton`), a `collectionApi` module in `apps/web/src/api/index.ts`, two new routes in `router.tsx`, a new `collections` tab on `UserProfilePage`, and an "Add to Collection" button on `RecipeDetailPage`. A "collections containing this recipe" section on `RecipeDetailPage` (US-9) is included as an optional task.
- **i18n**: new `collection.*` and `user.collections` keys added to both `en.json` and `tr.json`.
- **Reordering** uses up/down arrow buttons + optimistic `useFetcher` (no new drag-and-drop dependency — deferred to a follow-up).
- **Tests**: DB index/column assertions (`schema-indexes.test.ts`, `schema-columns.test.ts`), shared schema unit tests (`collection_test.ts`, `responses/collection_test.ts`), API model/service/route integration tests (real PostgreSQL, `deps`-swappable auth, `createTestApp` pattern), and frontend component/page tests.
- **Seed**: optional `seedCollections` helper in `seed.ts` (idempotent via `onConflictDoNothing` on the composite unique key), called from `main()`.

## Capabilities

### New Capabilities

- `recipe-collections`: Create, read, update, soft-delete, and reorder named collections of recipes. Collections have `private`/`unlisted`/`public` visibility. Any public recipe (not just the owner's) can be added to a collection. Duplicate recipe-in-collection is prevented by a composite unique constraint. Private/unlisted collections are visible only to the owner; public collections are visible to all visitors and appear on the owner's profile. Recipes can be reordered within a collection via `sortOrder`.

### Modified Capabilities

- `recipe-list`: (No query-path change.) `recipesRelations` gains a `collectionItems: many(collectionItems)` relation so a recipe can be queried for which collections contain it. This is additive and does not alter existing recipe list behaviour.

## Impact

- **Database**: New migration `0009_<codename>.sql` auto-generated by `make db-generate` (two `CREATE TABLE` statements + indexes + unique constraint + FKs). Applied via `make db-migrate`. No manual SQL. The migration creates `collection` and `collection_item` tables.
- **Shared schemas**: New `collection.ts` input-schema file + `responses/collection.ts` output-schema file. Both barrels (`schemas/index.ts`, `schemas/responses/index.ts`) gain explicit export blocks. No existing schema changes.
- **API**: New self-contained module — no changes to existing modules except `routes/index.ts` (one import + one `routes.route(...)` line) and `routes/openapi.ts` (one tag entry). The `usersRelations` and `recipesRelations` blocks in `packages/db/src/schema.ts` gain one `many(...)` line each (additive).
- **Frontend**: New pages/components are additive. `router.tsx` gains two routes. `UserProfilePage.tsx` gains a tab (one union member + one tab button + one conditional render block + one loader branch). `RecipeDetailPage.tsx` gains one button in the action-buttons row. `api/index.ts` gains a `collectionApi` object. `en.json`/`tr.json` gain keys. `robots.txt` generation in `vite.config.ts` may add `Disallow: /collections` (auth-only routes).
- **OpenAPI**: New `Collections` tag; 8 new documented routes. Coverage test updated.
- **Tests**: New test files across `packages/db`, `packages/shared`, `apps/api`, `apps/web`. Existing tests unaffected.
- **No third-party dependencies** — uses existing Drizzle, Hono, Zod, react-router, and hand-rolled modal patterns. No drag-and-drop library.
