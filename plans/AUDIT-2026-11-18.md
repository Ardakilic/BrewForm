# BrewForm Health Audit — 2026-11-18

> Full-codebase audit run as a multi-agent workflow. 7 parallel auditors each covered one area:
> plans/specs drift, API architecture, data layer, security, UI and visual design, web
> architecture, and DevEx/infra/CI. 2 adversarial verifiers then tried to refute every
> high/critical finding. **131 findings in total.** Of the 42 rated high/critical, 18 were
> confirmed and 24 were partially confirmed (real issue, but scope or severity adjusted); none
> were refuted. Severities below are the **post-verification** values. Duplicate findings from
> different auditors are merged. Every item cites `file:line` evidence that an agent opened and
> read, and the top items were re-checked by hand.
>
> Raw structured output (every finding, verifier reasoning, commands run) was saved in the
> session scratchpad as `audit.json`. It is temporary and will be lost on cleanup.

## 1. TL;DR

The codebase is **structurally healthy**:
- **Clean layering:** 20 of 21 API modules follow model → service → index, and no service
  imports `drizzle-orm`.
- **Clean checks:** `tsc` passes in every workspace, Biome fmt and lint exit 0, and
  `db:generate` reports no changes.
- **Healthy test base:** shared tests pass 727/727 and web tests 1346/1349; the 3 failures are
  host-ICU and flaky tests.
- **Disciplined migrations:** the 16 migrations have an unbroken snapshot chain.
- **Broad logging and good soft-delete discipline:** 154 `isNull(deletedAt)` call sites.

All of that hides a cluster of **real user-facing bugs and security gaps**, and none of them is
on the roadmap, because ROADMAP says "all debt resolved." The ten most important items:

| # | Issue | Sev | Effort |
|---|-------|-----|--------|
| 1 | **Any logged-in user can overwrite any recipe's notes.** `POST /recipes/:id/notes` has no owner check, and the UI shows the editor to everyone. | high | S |
| 2 | **Production first boot seeds 5 demo accounts with password `user123456`** (emails pre-verified). | high | S |
| 3 | **Rate limiting is bypassable and fragile.** It keys on the raw `X-Forwarded-For` header, runs on the optional cache (so it is off when `CACHE_ENABLED=false`), and a Valkey outage becomes an API outage. The memory Map never evicts, which is an OOM risk. | high | M |
| 4 | **S3 object key comes from the client filename**, so a server-signed PUT can escape the bucket. | high | S |
| 5 | **`compose.production.yml` loses data and won't boot.** Uploads are written outside the mounted volume, and empty `S3_*` strings fail env validation, so the default config crash-loops. | high | S |
| 6 | **5 admin pages crash on render.** `/admin` is mounted outside `ToastProvider`. | high | S |
| 7 | **Recipe list pagination is broken.** Next/Prev always lands on page 1, and a test codifies the bug. | high | S |
| 8 | **Recipe editing silently loses data.** Edits vanish unless "Bump Version" is ticked, a version bump drops taste notes, equipment and preparations, and `tds` is never stored. | high | M |
| 9 | **Slug de-dup is a no-op.** A duplicate title gives a 500, and a recipe can only be forked once. | high | S |
| 10 | **Charts render out of bounds.** Radar labels spill up to about 63px outside the viewBox, and BrewTimeline distorts text and has unbounded axis markers. | high | S–M |

Wave 0 below fixes about 15 of these in **1–2 days of S-sized work**.

## 3. P0: security and data-loss fixes

### 3.1 Recipe notes IDOR (high, S)
- `apps/api/src/modules/recipe/index.ts:846-873`: `authGuard` only. `userId` is never passed
  and there is no `isEmailVerified` check.
- `apps/api/src/modules/recipe/service.ts:711-718`: `saveNotes(recipeId, notes)` checks only
  that the recipe exists. There is no `authorId` check and no `sanitizeText`.
- `model.ts:1030-1035` overwrites `recipeVersions.personalNotes` in place, with no version
  history.
- `RecipeDetailPage.tsx:330-332` shows the editor to **every** logged-in user. The notes are
  public and feed search ranking.
- **Fix:** `saveNotes(recipeId, userId, notes)`: throw `FORBIDDEN` unless the caller is the
  author, sanitize the text, map the error to 403, and show the editor only to the author. If
  per-viewer notes were the intent, store them in a separate `user_recipe_notes` table.

### 3.2 Demo accounts with a known password in production (high, S)
- `docker-entrypoint.sh:19-26` runs the **full** seed whenever the users table is empty, with
  no environment guard.
- `seed.ts:229-262` + `seed-users-recipes.ts:9` (`defaultPassword = 'user123456'`) create
  alice, bob, charlie, diana and evan @example.com with `emailVerifiedAt` set, plus fake
  recipes, social data and brew logs.
- **Fix:** split the seed into `seed:base` (catalogs, badges, compatibility, taste notes, admin)
  and `seed:demo` (gated by `SEED_DEMO=true`, refused when `APP_ENV=production`). Add a
  runbook step to soft-delete `@example.com` accounts on existing deployments.

### 3.3 Rate limiter: spoofable, cache-coupled, unbounded (high, M)
- `middleware/rateLimit.ts:37-38, 89-90`:
  `ip = x-forwarded-for || x-real-ip || 'unknown'`, and the raw header string becomes the key.
  A random XFF value on each request means unlimited login, contact-form and comment attempts.
  Without a proxy in front, everyone shares the `'unknown'` bucket, so 5 bad logins lock out
  logins for everyone.
- `rateLimit.ts:41-51`: non-atomic get-then-set on `CacheProvider` with no try/catch. When
  `CACHE_ENABLED=false`, `NullCacheProvider` (`cache/index.ts:75-95`) means the counter never
  exceeds 1, so the limiter is off. With the redis driver, a Valkey restart stalls every
  request, `/health` included (the limiter runs on `*`).
- `utils/cache/index.ts:28-51`: `InMemoryCacheProvider` is a plain Map. It evicts only when a
  key is read again, and unique XFF keys are never re-read, so memory grows until OOM.
- `docs/deployment_coolify.md:282-285` incorrectly says "per-client limiting still works"
  behind Cloudflare.
- **Fix:** add a single `getClientIp(c)` helper driven by `TRUSTED_PROXY` config
  (`cf-connecting-ip` | right-most untrusted XFF hop | `getConnInfo()` socket address). Give
  the limiter its **own store**: Redis `INCR`+`PEXPIRE`, or a bounded LRU in memory. Make it
  fail open with a warn log and a circuit breaker. Key auth attempts by account as well as IP.
  Add an LRU cap and a periodic sweep to the memory cache. Fix the doc.

### 3.4 S3 key built from the client filename (high, S)
- `utils/upload/index.ts:53-58`: `ext = originalName.split('.').pop()`, with no allowlist.
- `utils/storage/s3.ts:27-33`: the URL is concatenated unencoded and then signed. The verifier
  reproduced `a.x/%2e%2e/%2e%2e/other-bucket/payload` resolving to `/other-bucket/payload`.
  R2 and Garage tokens are often account-wide.
- **Fix:** derive the extension from magic-byte-sniffed MIME (fixed map: jpeg→jpg, png, webp),
  restrict keys to `[A-Za-z0-9._-]`, URI-encode path segments, and send an explicit
  `Content-Type`. Apply the same to thumbnails. Related: photo upload skips `bodyLimit`,
  buffers the whole body, and never checks thumbnails (`bodyLimit.ts:15,61-66`).

### 3.5 `compose.production.yml` loses photos and won't boot (high, S)
- **Data loss:** `UPLOAD_DIR=./uploads` (`:113`) resolves against cwd `/app/apps/api`, because
  `pnpm --filter exec` sets cwd to the package. The volume is mounted at `/app/uploads`
  (`:116-117`), so every photo lands in the container layer and is lost on recreate.
- **Boot failure:** `S3_ENDPOINT: ${S3_ENDPOINT:-}` injects `''`, and `env.ts:64,69`
  (`z.url().optional()`) rejects it, so the default local-storage config crash-loops.
- **Fix:** default `UPLOAD_DIR=/app/uploads` (and resolve it to an absolute path in `env.ts`,
  logged at startup). Preprocess `''` → `undefined` for optional env URLs. Add an `env.test.ts`
  case.

### 3.6 Insecure env template and admin exposure (medium, S, cheap to fix)
- **Env template:** `apps/api/.env.example` is labelled "paste into Coolify". It has
  `APP_ENV=production`, `JWT_SECRET=change-me-…` (passes `min(16)`),
  `ADMIN_PASSWORD=admin123456` and `OPENAPI_ENABLED=true`. Nothing rejects placeholders in
  production.
- **Public profile:** `user/service.ts:55` strips only `passwordHash`/`email`, so `id` and
  `isAdmin` are public. A leaked secret plus a public admin UUID gives a forged admin token.
- **Admin responses:** `admin/model.ts:114-141, 179-190, 228-233` `.returning()` every column,
  so admin user endpoints return **`passwordHash`**. The self-edit guard is bypassable via the
  role and ban routes.
- **Verification email:** `POST /auth/send-verification` has no rate limit, so it can mail-bomb
  through your SMTP.
- **Fix:** refuse to boot in production with placeholder or short secrets. Blank the template
  values. Use an allowlist projection for public profiles and admin responses. Rate-limit
  send-verification.

### 3.7 Auth session hygiene (medium, M)
- Refresh tokens are bare `{sub,type}` JWTs, valid up to 180 days, and remember-me tokens renew
  themselves indefinitely (`auth/jwt.ts:64-74`, `service.ts:153-183`). ADR-003 accepts
  "no server-side revocation", but **a password reset doesn't kill sessions**, which is the
  standard recovery path for a compromised account.
- Reset tokens are stored in plaintext and consumed in two unguarded statements
  (`auth/model.ts:102-128`), unlike the hashed, atomic email-verify tokens.
- Login and forgot-password allow account enumeration through timing and ban-check ordering
  (`service.ts:115-127`). bcrypt runs synchronously (`compareSync`).
- **Fix:** add a `users.tokenVersion` column, embed it in both tokens, check it in
  `authMiddleware` and refresh, and bump it on reset, admin password change, and a new
  "log out everywhere" action. Hash reset tokens and consume them with
  `UPDATE … WHERE usedAt IS NULL RETURNING`.

## 5. Charts and visual design deep-dive

### 5.1 `ScaaRadarChart`: labels out of bounds (high, S)
`apps/web/src/components/recipe/ScaaRadarChart.tsx`
- `:22-23`: `MAX_RADIUS = 100` per 300 box (radius = size/3) and `LABEL_RADIUS_FACTOR = 1.15`.
  **No padding is reserved for label width.**
- `:101-107`: `viewBox="0 0 size size"`, `width={size}` (fixed px), and
  `style={{overflow:'visible'}}`, so labels paint outside the box instead of being fitted.
- `:150-159`: fixed `fontSize={10}`, `text-anchor` start or end, and a raw English `{cat}`
  label (not translated).
- **Measured:** at `size=200`, "Green/Vegetative" (axis 6, 150°) is end-anchored at x≈33.6.
  At about 5.5px per character for 16 characters it reaches **x≈−55**, and "Sour/Fermented"
  reaches about −50. "Nutty/Cocoa" overruns on the right and touches the chip list.
- **Fix:**
  ```tsx
  // split long labels on '/' into two <tspan> lines → max ≈ 10 chars ≈ 52px
  const pad = maxLabelWidthPx + 4;
  <svg viewBox={`${-pad} ${-pad/2} ${size + 2*pad} ${size + pad}`}
       width="100%" style={{ maxWidth: size + 2*pad, display: 'block' }}>  // no overflow:visible
  ```
  Also: scale `fontSize` with `size`, translate category labels via `t()`, and clamp values to
  `[0, max]`, treating `NaN` as 0 (a later check for `radar-chart-data.ts`).

### 5.2 `BrewTimeline`: distorted text, unbounded ticks, no clamping (high, M)
`apps/web/src/components/recipe/BrewTimeline.tsx`
- `:142-147`: `viewBox="0 0 1000 120"` with `preserveAspectRatio="none"`, width 100% and
  height 80px. The `<text>` at `:199-244` is inside this non-uniformly scaled SVG, so on a
  ~277px mobile card glyphs render at **about 41% of their natural width** (scaleX 0.277 vs
  scaleY 0.667), and at about 75% on desktop.
- `:9-25`: `generateAxisMarkers` caps the step at 30s with **no limit on marker count**. A 12h
  cold brew (43,200s, which the API accepts as `z.number().positive()`) gives **1,441 labels**,
  and any brew over about 300s collides. The total is always appended, so near-duplicate
  markers overlap.
- `preInfusion ≥ total` produces negative segment widths and draws the curve off-chart.
- **Fix:** keep only the area and stroke paths in the stretched SVG
  (`vector-effect="non-scaling-stroke"`) and render labels as absolutely-positioned HTML. Pick
  ticks from a nice-step list (`[5,10,15,30,60,120,300,600,1800,3600…]`), targeting 8 or fewer.
  Clamp `pre = min(preInfusion ?? 0, total − 1)` and `pct = clamp(0, 100, pre/total·100)`.

### 5.3 Recommendation: one chart primitive
F17 (admin analytics, whose 5 endpoints exist with **no UI**) and F03 (profile stats) will both
need charts. Build **one** responsive, viewBox-padded SVG chart primitive with a shared
`clamp()`, nice-tick and label-fit helpers, and a test harness that asserts every
`<text>` bbox stays inside the viewBox. Then port the radar chart and timeline to it. That
prevents this class of bug from coming back.

## 6. Architecture pain points (P2)

Grouped by theme. These are the structural causes behind many of the bugs above.

### A. Authorization and visibility rules are duplicated
`canViewRecipe` (`recipe/service.ts:767-776`) coexists with inline variants with **different
semantics** in collection, comment and photo code. Like, favourite, rate and photo-list skip
visibility entirely (`service.ts:660-697`). Fork links and status codes act as existence oracles.
→ Create **one policy module** (`canView`, `canEdit`, `canInteract`) used by every service,
with a table-driven test matrix (owner, other, admin, anonymous × public, unlisted, private,
draft, deleted).

### B. The error contract is stringly typed
There are 121 `throw new Error('UPPER_CASE')` sites and 121 `message === '…'` comparisons across
67 try/catch blocks in routers. 52 of 91 `zValidator` uses skip the standard error envelope, and
some service errors fall through to 500.
→ Add an `AppError` hierarchy (`NotFound`, `Forbidden`, `Conflict`, `Validation`) mapped once in
`errorHandler.ts`, plus a shared `zValidator` hook for the envelope. That deletes most router
try/catch code.

### C. The admin module duplicates domain CRUD and bypasses its invariants
`admin/model.ts` (803 lines), `service.ts` (724) and `index.ts` (688) re-implement other
domains:
- **Invariants skipped:** system coffee varieties are editable and deletable from admin even
  though the domain says they're immutable (`admin/service.ts:642-662` vs
  `coffee-variety/service.ts:99-170`).
- **Stale cache:** the 24h variety cache isn't invalidated.
- **Wrong status codes:** `resolveReport`/`dismissReport` return `null`, so the 404/409
  mappings are dead.
→ Make admin an **orchestration layer** over the domain services (`isAdmin=true`), with an
audit log after each call. Delete the duplicated writes.

### D. The recipe module is the hotspot
`recipe/model.ts` 1,298 lines, `service.ts` 1,005, `index.ts` 930.
- **Non-atomic writes:** version creation runs as separate statements, validation happens
  after insert, and orphan versions show up on the detail page (`service.ts:299-351`).
- **Over-fetching:** `findById` loads the full version tree just for authz checks
  (`model.ts:311-330`).
- **Mixed filter semantics:** some filters match any historical version, others only the
  current one (`model.ts:104-165`).
→ Split into `recipe-query`, `recipe-write` (transactional) and `recipe-social`. Add a slim
`findAuthzById`.

### E. Search doesn't scale
`findAllForRanking` (`service.ts:586-603`, `model.ts:410-432`) loads **every matching public
recipe and all its versions** into memory per request, ranks in JS, and then slices one page.
It uses leading-wildcard `ILIKE` with no statement timeout, on a 10-connection pool.
→ Short term: cap the candidate set (for example, the top 500 by recency) and set
`statement_timeout`. Longer term: this conflicts with the AGENTS.md rule *"no Postgres-specific
operators in application query code"*. Either write an ADR to allow a generated `tsvector`
column or `pg_trgm` (the real fix), or keep app-level ranking and maintain a denormalized
search column.

### F. Caching is wired three different ways
The codebase uses a singleton import (equipment), a singleton passed as a parameter (taste),
and a context variable (`c.set('cache')` in `main.ts:77-80`, **never read**). Some caches and
invalidations are dead, and admin "flush all" misses most keys.
→ Pick one pattern (DI through the context variable matches the AGENTS.md rule), centralize key
builders, and make "flush" use namespace prefixes.

### G. Data integrity drift
- `likeCount`, `commentCount` and `forkCount` drift: deleting a comment orphans its replies but
  decrements by 1, there is no non-negative guard, and the seed starts out of sync. → Add a
  nightly reconcile job and `CHECK (count >= 0)`.
- **No `updatedAt` column has `$onUpdate`**, so recipes, users, comments and others never bump
  it, and sitemap `lastmod` is wrong. → Add `.$onUpdate(() => new Date())`.
- Email and username uniqueness is case-sensitive (fixed together with the partial unique
  indexes in §4).
- Keyset cursors truncate timestamptz µs → ms, so rows can be skipped (`model.ts:1128-1132`).
- About 30 redundant indexes duplicate unique constraints or left prefixes
  (`schema.ts:95-96,166,932`, etc.).

### H. Notification spam
Every like/unlike or follow/unfollow toggle creates a **new notification and email**, with no
dedupe (`recipe/service.ts:660-683`). → Upsert on `(type, actor, target)` and add an email
cooldown.

### I. Background work isn't multi-instance safe
- **Cron:** runs on every replica with no lock or overlap guard, and is registered as an
  import side effect of `main.ts` (`utils/jobs/cron.ts:10-21`).
- **Migrations:** run on every container boot with no lock, and the image build runs
  `drizzle-kit generate` (`Dockerfile:35`).
- **Email:** sent synchronously with nodemailer's default multi-minute timeouts
  (`notify/index.ts:53-63`).
→ Add a Valkey `SET NX PX` lock for cron (required before F29 weekly digest or F30). Run
migrations as a one-shot init job. Configure SMTP timeouts and move email off the request
path.

### J. The web data layer is half-migrated
13 routes use react-router loaders and actions, while about 30 pages, including all 11 admin
pages, still use `useEffect` + `useState` with **no AbortController, no dedup, and no
stale-response guard** (only 4 files guard). Other problems:
- **Static cache:** `static-cache.ts` re-broadcasts the cross-tab storage event on receipt,
  causing ping-pong (`useStaticCacheSync.ts:20-27`).
- **Search input:** search and author filters push history and refetch on **every keystroke**
  (`RecipeListView.tsx:275,362`).
- **Auth routes:** auth-guarded loaders show the error page instead of redirecting to login,
  and there is no return-to after login.
- **Token refresh:** the API client has no single-flight refresh, so N parallel 401s trigger N
  refresh POSTs (`client.ts:47-62`).
→ **Decide**: finish the loader migration (with `shouldRevalidate`, abort signals and a
`redirect('/login?next=')` helper) **or** adopt TanStack Query as D10 originally planned. Don't
keep both. Debounce text filters at 300ms.

### K. The recipe form is duplicated
`RecipeCreatePage.tsx:35-65` and `RecipeEditPage.tsx:36-59` each hold about 25 near-identical
`useState` fields and payload builders. Shared Zod schemas are barely used client-side, and 21
files bypass the D42 typed boundary with 29 ad-hoc `api.*` calls.
→ Build one `<RecipeForm>` with a reducer, validated by `RecipeCreateSchema`/`RecipeUpdateSchema`.
Add the missing typed methods to `api/index.ts`.

### L. Test suite blind spots
- **Tests that codify bugs:** the pagination test, and an error-handler test that fabricates
  the wrong error shape.
- **Tests of copies:** about 1.5k lines exercise copies of logic instead of production code
  (`FollowButton.exploration.test.ts`, which is also excluded from the run).
- **No end-to-end coverage:** no router-level smoke test (which would have caught the admin
  crash) and no e2e suite.
→ Add one `createMemoryRouter(routes)` smoke test per route with the real providers. Add a
small Playwright suite for create recipe → edit → paginate → comment → admin moderation.
